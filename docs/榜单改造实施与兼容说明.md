# 榜单改造实施与兼容说明

对应“瞄瞄改为榜单”方案，首页头部背景按门店独立配置。

## 代码入口

| 仓库 | 入口与职责 |
| --- | --- |
| dudu-uniappx-app | `pages/find/Find.uvue` 保留原 Tab 路由；`pages/goods/TopList.uvue` 读取新版详情与分页定位；`common/rank.uts` 负责统一跳转、图片与分组；公共商品卡复用榜单关联标签 |
| dodo-supermarket-frontstage | `web-starter/.../ad/controller/RankController.java` 提供新版用户接口；`ad/service/logic/RankReadService.java` 组装展示数据；商品服务统一选择关联榜单 |
| dodo-supermarket-backend | 原榜单管理中的“首页与标签设置”入口，`src/components/ad/RankSettings.vue` 维护完整门店快照、背景、推荐、标签和排序 |
| dodo-supermarket-backstage | `ad/controller/RankAdminController.java` 提供配置和商品预览；原榜单增删改、发布、商品替换和导入接入同一门店事务与版本 |
| framework-java/business-core | `com.dodosupermarket.rank.RankService` 为共享规则入口；DAO 使用具名 MyBatis Mapper，常规 CRUD 复用 GenericService/GenericDAO。Maven 产物仍为 `dodo-business-core` |

## 页面和排名

- 首页背景来自 `homepageBackgroundImage`，独立于榜单 `backgroundImage` 和 `topUrl`。标题、搜索和安全区由前景布局负责，背景图片不负责点击。
- 三个推荐位固定为左大、右上、右下。分别取本榜第 1～3、1～2、1～2 名；不显示价格和购买按钮。未配置留在原位置，不调换位置、不跨榜补商品。
- 标签切换只更新下方分组，不改变推荐位。“全部”按标签分组，同榜可以跨组出现，组内去重。
- 下方榜单预览展示前三名真实商品，沿用购买组件。商品图片和名称进入商品详情，榜单标题和完整榜单按钮进入榜单详情。
- 排名先按原商品关系排序生成，再过滤不可展示商品。缺货保留名次；隐藏商品不会让后续商品重新编号。前三名中有商品不可展示时，不用第四名补位。
- `boardRank` 表示当前列表所属榜单的真实名次；既有 `topId/topName/topRank` 表示商品按已发布榜单关联优先级选出的默认关联，二者不可混用。
- 详情优先使用入口标签；标签无效时选该榜单第一个有效标签，否则导航展示全部有效榜单。跨页定位返回实际页码，客户端加载该页后滚动并高亮，商品不置顶。
- 标签关闭只隐藏分组入口，榜单和商品关联仍可使用。无商品的榜单不进入聚合导航；无有效榜单的标签不进入首页导航。

## 旧接口兼容边界

原用户接口 `/api/ad/themeTopList/get`、`/goods`、`/tabName` 及 v3 `/forSearch` 保留路径、原参数和 `R` 返回信封。特别保留旧 `/tabName` 把指定榜单移到第一项、`test/dev` 预览环境和旧商品接口原分页规则。新详情保持导航顺序的规则只适用于独立新版接口。

原推荐接口保留 `rank` 类型、选榜与插卡节奏，向榜单对象追加真实 `goodsList`。门店不匹配或选榜后并发下线时，附加预览为空，不因附加数据的资格校验导致旧推荐请求失败。原图片字段继续保留。新增榜单商品的补货状态在 Controller 中复制商品后补齐，不修改公共缓存中的对象。

原商品接口继续返回 `topId/topName/topRank`，修复为同一条有效关联的 ID、标题、名次，并按当前门店已发布榜单优先级选择。新增 `boardRank` 是可选展示字段。

原管理接口继续使用原 URL、表单和响应信封；`expectedVersion` 为新增可选参数，旧调用无需补交。未传时在门店锁内读取当前版本并递增；传入时严格检查。新建旧表单自动补齐优先级和综合标签。商品保存与导入增强校验会拒绝重复 SKU、无效商品、缺失或重复排序，并保留原数据。

## 用户新版 API

门店和销售网点来自当前登录/选店方案，不接受调用方任意覆盖。返回均为既有 `R` 信封，业务结果在 `data`。

| GET 路径 | 参数 | `data` 字段 |
| --- | --- | --- |
| `/api/v3/ad/rank/home` | 无 | `version`、`homepageBackgroundImage`、`tags`、`recommendations` |
| `/api/v3/ad/rank/collections` | `tagId` 可空；`pageNum=1`；`numPerPage=10` | `groups`、`pageNum`、`hasMore` |
| `/api/v3/ad/rank/detail` | `id`；`tagId` 可空 | `available`、`board`、`navigation`、`tagId` |
| `/api/v3/ad/rank/goods` | `id`；`pageNum=1`；`numPerPage=20`；`focusGoodsId` 可空 | `goodsList`、`pageNum`、`hasMore`、`focusFound` |

`recommendations` 每项为 `{position, board, goodsList}`，按 `position` 绑定固定位置。`groups` 每项为 `{tagId, tagName, boards}`，每张榜单卡包含 `{id, title, tagId, goodsList}`。集合分页单位为“标签中的一个榜单”，同一标签可能分布在相邻页，客户端按标签合并、组内按榜单 ID 去重。

分页尺寸允许 1～100。定位商品存在时，商品接口覆盖 `pageNum` 为目标所在可展示页；不存在时返回正常请求页并令 `focusFound=false`。下线或空榜详情返回 `available=false`，客户端展示返回榜单首页入口。

商品价格、起购、限购、促销、库存展示经过原商品服务。新版展示接口返回前补齐当前用户补货订阅，不写入公共缓存。原商品/主题/推荐缓存键加入门店榜单版本，并保留门店、网点隔离。

## 管理新版 API 与失败恢复

- `GET /api/ad/rank/settings`：读取门店完整设置，包括版本、首页背景、全部榜单和全部标签关系。
- `POST /api/ad/rank/settings`：JSON 提交完整设置。必须携带 `version`、全部现存榜单 ID 和完整标签数组。榜单只保存展示排序、关联优先级和推荐位置；不覆盖标题、发布状态或详情图片。新标签 ID 使用 `null`，移除标签以省略表达。
- `GET /api/ad/rank/preview?id=...&limit=3`：返回真实商品预览和 `boardRank`，用于配置界面预览。

保存成功返回新版本的完整设置。冲突为 HTTP 409，`data.error=VERSION_CONFLICT`；其他校验错误返回具体原因。冲突或网络结果不确定时重新读取完整配置并核对，再修改保存，不能盲目重试覆盖。前端保留未保存内容并提示重新读取。

背景图使用原上传组件和临时图转存流程。首页背景和详情背景分别保存。空字符串清空首页背景，客户端使用内置默认图。

配置、商品替换、导入和排序在同一门店事务内执行，先获取配置行锁，再校验显式版本，成功后递增一次。任一步失败回滚业务数据和版本。已发布榜单关联优先级为门店内唯一正整数；推荐位置仅允许已发布榜单使用唯一的 1～3。下线解除其推荐位。

## SQL 和切换顺序

1. 统一入口为 `db/test/05-rank.sql`。将顶部 `rank_action` 改为 `check`，处理全部阻断问题；详细结果的 `severity=BLOCK` 需要修复，`INFO` 为允许的历史状态。改为 `preview` 可预览排序变化，改为 `status` 可查看当前结构；也可选中相应 BEGIN/END 标记内的 SELECT 单独只读执行。
2. 备份并选择业务停写窗口，将 `rank_action` 保持为默认 `migrate`，整份执行 `db/test/05-rank.sql`。包含完整五表、历史升级、菜单及原角色授权，可重复执行，不包含模拟数据。需要 MySQL 8.0.16+ 和 CREATE ROUTINE 权限；禁止使用 `--force` 忽略保护检查。DDL 隐式提交，不承诺脚本整体回滚。
3. 构建共享 `dodo-business-core`，再部署兼容服务端与管理端。保留原榜单 ID、商品关系和接口；历史数据按原顺序生成唯一展示顺序与关联优先级，归入综合标签。
4. 后台明确选择推荐位、上传首页背景，再发布新版 App。初始推荐位为空、首页使用默认背景。

历史失效或软删除商品保留关联并由用户端隐藏，不阻断迁移；真正缺失的商品记录、错误门店、SKU 不匹配、空值及重复商品/SKU 仍阻断。存在有效关系排序冲突的榜单按原 `sort_order ASC, id DESC` 顺序重排，不删除关系、不修改商品状态；没有冲突的榜单不改商品排序。
