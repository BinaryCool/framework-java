# 嘟嘟业务 SQL 执行说明

更新日期：2026-11-09。适用文件：本目录的 `01-business.sql`～`05-rank.sql`。

这些文件用于已有商城环境的共享业务安装和更新，直接在数据库客户端执行，不需要 PowerShell 脚本。它们不负责建立整套商城基础库，应用启动也不会自动执行这些 SQL。

## 一、执行顺序与目标库

| 顺序 | 文件 | 连接的数据库 | 执行内容与顶部选项 |
| --- | --- | --- | --- |
| 1 | `01-business.sql` | 业务主库 | 晒单、补货、问卷完整建表及旧表更新，无需修改选项 |
| 2 | `02-im.sql` | 应用实际使用的 IM 库，默认日志库 | IM 完整建表及历史字段、索引更新，无需修改选项 |
| 3 | `03-menu.sql` | 业务主库 | IM、晒单、问卷、补货菜单及原有角色授权，无需修改选项 |
| 4 | `04-analytics-business.sql` | 业务主库 | 无需修改选项，整份执行 |
| 5 | `04-analytics-log.sql` | 日志主库 | 无需修改选项，整份执行 |
| 6 | `05-rank.sql` | 业务主库 | 旧环境先用 `check` 和 `preview` 检查，再将 `rank_action` 改回 `'migrate'` 整份执行 |

只更新其中一项业务时，可以执行对应文件；相关表和商城基础表必须已经具备。只更新榜单时，`05-rank.sql` 自带榜单菜单，不需要为了榜单再次执行 `03-menu.sql`。

业务库、日志库可能在不同服务器或端口。SQL 不会替你切换连接或数据库；每次执行前都要确认当前客户端连接和选中的库。IM 五张表共用 `dudu.im.jdbc-url` 指定的独立连接。前后台仅 local 配置默认引用日志库写地址，且可由 `DUDU_IM_JDBC_URL` 覆盖；仓库内其他环境未配置或启用该 IM 连接，部署时必须明确指定。不要仅根据库名猜测。

## 二、执行前准备

1. 使用 MySQL 8.0.16 或更高版本，连接可写主库。业务库应已有商城基础表，包括 `store`、`dodo_operate_log`、`dodo_order_info`、`dodo_goods` 及菜单角色表；不同文件按需使用这些表。
2. 备份将要修改的表结构和数据。旧榜单首次迁移尤其要备份两张主题榜单表、已有三张 `dodo_rank_*` 表以及菜单、角色菜单关联。
3. 执行账户需具备对应的建表、改表、索引及数据读写权限。整份执行 `05-rank.sql` 还需要创建、执行和删除存储过程的权限；两份 analytics SQL 均不需要存储过程权限。
4. 将客户端设为遇错停止；不要选择忽略错误继续，不要使用 `--force`。包含 `DELIMITER $$` 的文件应使用客户端的“执行脚本”功能，并保持整个文件使用同一连接。
5. 线上旧榜单首次迁移应安排业务停写窗口。表结构及索引变更也可能等待锁或影响查询，不应把“可重复执行”理解成“线上零影响”。

可先单独执行以下只读语句，核对连接信息：

```sql
SELECT DATABASE() AS current_database,
       @@hostname AS server_host,
       @@port AS server_port,
       VERSION() AS mysql_version,
       @@read_only AS server_read_only;
```

当前库为空时，先在客户端选中正确数据库。`read_only = 0` 只是核对项，不能代替确认连接的是目标主库。

## 三、各文件的实际修改范围

### 01-business.sql：晒单、补货、问卷

| 业务 | 表 |
| --- | --- |
| 晒单 | `dodo_show_activity`、`dodo_show_submission`、`dodo_show_activity_log` |
| 补货 | `dodo_restock_subscription`、`dodo_restock_notice`、`dodo_restock_supply` |
| 问卷 | `dudu_survey`、`dudu_survey_version`、`dudu_survey_ticket`、`dudu_survey_response` |

已有表不会删除重建。脚本会将原为 VARCHAR 的 `dodo_operate_log.operate_content` 扩容为 TEXT；给旧问卷补充游客字段、更新去重索引，并同步问卷表和字段的中文注释。保留历史业务记录，不清空问卷答卷。

`CREATE TABLE IF NOT EXISTS` 不会自动修复任意版本的旧表结构。文件只覆盖其中明确写出的历史升级；如果实际结构与预期差异较大，应先核对差异。

### 02-im.sql：IM

包含 `im_conversation`、`im_lease`、`im_participant_read`、`im_send`、`im_attachment` 五张表。旧版本补充会话同步标记、租约发言角色及对应巡检、重试索引。

不会清空会话、租约、发送台账或附件记录；已有 `sender_role` 不会被统一覆盖成默认角色。

### 03-menu.sql：共享菜单

维护 `/customer/im`、`/customer/ShowPage`、`/customer/show`、`/customer/surveys`、`/log/GoodsNoticeReplenish` 五个页面及其父菜单。

复用已有页面 ID，但会按脚本更新这些页面的名称、父节点、排序、图标和启用状态，并为指定的已有角色补齐或恢复菜单授权。不会创建角色，也不会修改员工与角色的对应关系。原先停用的目标菜单或授权可能被重新启用。

### 04-analytics-business.sql：业务主库

连接业务主库，整份执行。会创建或升级 `dodo_analytics_outbox`、`dodo_analytics_payment_scan`，同步中文注释，补齐订单扫描所需索引，并维护 `/log/AnalyticsEvents` 菜单及 admin 角色授权。等价索引已存在时不重复建立；已有行为明细页面保留原位置。

无需修改任何选项，也不需要存储过程权限。台账投递状态和扫描游标保持原值。

### 04-analytics-log.sql：日志主库

连接日志主库，整份执行，无需修改任何选项。会创建或升级 `analytics_event`，将事件 ID 调整为 `utf8mb4_bin` 精确匹配，并补齐门店、接收时间索引，保留历史事件。

这份文件不依赖商城业务表，不处理业务台账或菜单，不需要存储过程权限。两个 analytics 文件可以在不同服务器或端口分别执行。

### 05-rank.sql：榜单

包含两张原有榜单表 `dodo_theme_top_list`、`dodo_theme_top_goods_ref`，以及三张配置表 `dodo_rank_config`、`dodo_rank_tag`、`dodo_rank_tag_board`。包含榜单菜单及原有管理角色授权，不含模拟数据。

| `rank_action` | 用途 | 是否修改业务表 |
| --- | --- | --- |
| `status` | 查看相关表和榜单新增字段是否存在 | 否 |
| `check` | 返回阻断问题和逐条历史关系诊断 | 否 |
| `preview` | 预览存在有效关系排序冲突的榜单将如何重排 | 否 |
| `migrate` | 完整建表、补字段、首次初始化及菜单更新，文件默认值 | 是 |

这些模式同样需要修改**文件顶部**的 `SET @rank_action = ...` 后整份执行。整份文件会临时创建过程；若只需要纯只读查询，也可以单独选中 `BEGIN RANK_STATUS`、`BEGIN RANK_PREFLIGHT`、`BEGIN RANK_DETAILS` 或 `BEGIN RANK_PREVIEW` 与对应 END 注释之间的 SELECT 执行，不要包含存储过程外层。

旧榜单更新顺序：

1. 先执行 `status`，保存当前结构状态。
2. 执行 `check`。第一个结果集列出迁移阻断问题，应为空；详细诊断中的 `BLOCK` 及最后结果集中的门店缺失、已发布空榜等问题需要处理。仅有 `INFO`（例如排序冲突、历史失效或软删除商品）不阻断。
3. 执行 `preview`，保存并核对原排序值、新排序值和关系 ID。
4. 备份并停止榜单相关写入，将顶部改回 `SET @rank_action = 'migrate';`，整份执行。

首次初始化以**执行前是否缺少 `association_priority` 字段**为判断依据。首次迁移会：

- 为旧榜单按原 `sort_order ASC, id DESC` 生成排序和关联优先级，并将推荐位设为 NULL。
- 只对有效商品关系存在重复排序的榜单重排该榜单全部关系；按同一规则保持关系的相对先后，不删除历史关系。
- 补充门店配置、综合标签及有效榜单的标签关系。
- 更新“系统管理 / 主题馆 / 榜单列表”菜单，并为 `admin`、`sys_admin`、`admin_market` 补齐或恢复相关菜单授权。已有榜单页面的父节点、排序等会按脚本更新。

已存在 `association_priority` 时，正常重跑不执行上述首次排序、优先级及标签初始化，但仍补齐缺失结构、门店配置和菜单。脚本不修改商品、库存、价格或订单；涉及更新且原表带自动更新时间的记录，其更新时间可能随更新变化。

因此，榜单升级保留原榜单及商品关系，但首次迁移会修改部分旧数据，不能视为完全无影响。

## 四、执行后如何验收

1. 保存每份文件的执行日志。出现错误立即停止，不能只看客户端最后一条“执行完成”。
2. 核对目标表是否齐全。两份 analytics 文件最后会返回目标库及更新结果；05 的 migrate 成功时会返回“榜单建表及升级完成”。
3. 榜单再次执行 `status` 和 `check`，核对字段、阻断问题、原榜单 ID、商品关系数量及页面展示顺序；首次迁移的推荐位为空是预期，需要后台重新配置推荐位。
4. 用相应角色重新登录后台，核对菜单与页面访问；共享菜单只给脚本列出的已有角色授权，不会自动为任意角色开放权限。
5. 开启相关服务后，验证问卷提交、IM 会话、晒单及补货功能。Analytics 需确认扫描游标推进、台账投递正常、日志库能收到事件；SQL 本身不启动扫描，也不保证补采历史付款订单。

## 五、出错与恢复

**DDL 会隐式提交，整个文件不能靠一次 ROLLBACK 全部撤回。** 文件可重复执行是指正常完成后的常规重跑，不代表任意中途失败都能自动恢复。

| 现象 | 处理方式 |
| --- | --- |
| 表不存在、字段不存在 | 先核对连接、目标库、商城基础表及历史结构；不要临时随意建一张同名空表绕过错误 |
| 权限不足或 DELIMITER 报语法错误 | 核对执行账户权限与客户端脚本模式，停止后确认已经执行到哪一步 |
| `rank preflight failed` | 当前阻断发生在榜单业务表结构和数据变更前；执行 check，核对并修复阻断记录后再迁移 |
| 唯一索引或约束冲突 | 保留原记录，核对重复值及其归属后处理；不要直接删除历史数据让脚本通过 |
| ALTER 等待锁、连接中断 | 先检查数据库中语句是否仍在运行，以及实际结构和事务状态，避免并行启动另一份相同脚本 |
| 05 添加字段后在后续阶段失败 | 先执行 status，并检查配置、标签和旧榜单数据。新增字段已提交，但初始化事务可能回滚；重跑会因字段已存在而跳过首次初始化，需要根据实际提交状态单独制定补齐或恢复方案，不能盲目重跑 |

需要恢复时，依据执行前备份及实际已提交的修改处理。不要通过删除新增表、删除 `association_priority` 字段来强行触发初始化；这可能丢失已投入使用的配置或覆盖现有榜单。
